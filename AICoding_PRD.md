# AI 需求交付控制台 — 产品需求文档 (PRD)

> **版本**: v1.0
> **日期**: 2026-06-11
> **受众**: 管理层/决策者

---

## 1. 一页纸摘要

### 1.1 产品定位

AI 需求交付控制台是一个 **AI 驱动的软件需求交付管理平台**，将需求从 PRD 分析到代码评审的全流程结构化、可视化、可追溯，通过 AI Agent 加速每个阶段的产出，人工把控关键门禁，实现"**AI 主导产出，人工主导决策**"的协作模式。

### 1.2 核心价值

```
                      ┌──────────────────┐
                      │  AI 交付控制台    │
                      │     核心价值      │
                      └────────┬─────────┘
                               │
               ┌───────────────┼───────────────┐
               │               │               │
               ▼               ▼               ▼
        ┌────────────┐  ┌────────────┐  ┌────────────┐
        │  效率提升  │  │  质量保障  │  │  过程透明  │
        │           │  │           │  │           │
        │ AI 加速   │  │ 4 阶段门禁│  │ 实时协作  │
        │ 全流程    │  │ AI+人工   │  │ 产物可追溯│
        │ 产出效率  │  │ 双重把关  │  │ 进度可视化│
        └────────────┘  └────────────┘  └────────────┘
```

| 价值维度 | 现状痛点 | 控制台解决方案 |
|---------|---------|--------------|
| **效率提升** | 需求→交付靠人工串联，文档分散，反复沟通 | AI 一键生成 PRD 分析、技术方案、实施任务、代码评审 |
| **质量保障** | 评审靠自觉，遗漏多，缺陷到测试阶段才暴露 | 4 阶段门禁机制，前置审批才放行，AI 自动检查问题 |
| **过程透明** | 需求进度靠问人，产物散落各处，无法追溯 | 需求维度聚合并可视化所有产物，实时协作可见 |

### 1.3 核心数字

- **4 个交付阶段**：PRD → 技术方案 → 实施 → 代码评审
- **15 种 AI 动作**：覆盖从需求分析到代码评审的全链路
- **4 种 AI Agent**：Codex / CodeBuddy / Qoder / Qwen，按场景选用
- **4 种执行模式**：后台运行 / 终端 / 交互终端 / 手动复制

**辅助动作（不绑定特定 Skill）：**

| 动作 | 说明 | 输入 → 输出 |
|------|------|------------|
| `OPENSPEC_STATUS` | 检查变更状态 | 变更名称 → 变更当前状态摘要 |
| `OPENSPEC_INSTRUCTIONS` | 查看 OpenSpec 操作指引 | 无 → 操作说明文本 |
| `RETURN_TO_IMPLEMENTATION` | 回退到实施阶段 | 需求编号 → 阶段状态回退 |
| `REFRESH_ARTIFACTS` | 刷新产物索引 | 需求编号 → 产物列表更新 |

### 3.1 场景一：需求创建与管理

**目标**：快速创建需求，关联项目与分支，统一管理需求池

```

│  └─────────┘     │ • 需求ID    │     │ 开始 PRD 阶段工作    │  │
│                  │ • 需求标题   │     └──────────────────────┘  │
│                  │ • 类型(需求/ │                               │
│                  │   缺陷)     │     ┌──────────────────────┐  │
│                  │ • 分支名    │     │ 缺陷类型特殊处理      │  │
│                  │ • 关联项目  │      │ 跳过PRD阶段           │  │
│                  └─────────────┘    │ 直接从技术方案开始    │  │
│                                     └──────────────────────┘  │
│                                                                  │
│  ┌─────────────────────────────────────────────────────────┐    │

│  │  │171635│ 会员  │ 需求 │feat/ │ PRD  │ 👤3  │ 编辑 │     │     │
```

**交互要点**：
- 需求 ID + 标题为必填，分支名自动生成（可修改）
- 支持需求（REQUIREMENT）和缺陷（DEFECT）两种类型
- 缺陷类型自动跳过 PRD 阶段，从技术方案开始
- 需求列表支持多维度筛选和分页
- 协作列显示在线人数和待处理评审数

## 11. 非功能需求

| 维度 | 要求 |
|------|------|
| **性能** | 需求列表加载 < 2s，产物预览 < 1s，SSE 日志延迟 < 1s |
| **并发** | 同一需求并发锁保护，不同需求可并行执行 |
| **安全** | 路径穿越防护，SSH 密钥本地隔离，产物 Hash 校验 |
| **兼容** | 支持 macOS / Windows / Linux，桌面端集成可选 |
| **可用性** | 本地服务异常时前端降级提示，WebSocket 断线自动重连 |
| **可观测** | 全链路运行日志，产物版本追踪，环境诊断 |

## 12. 术语表

| 术语 | 说明 |
|------|------|
| **需求** | 一个功能需求或缺陷，有唯一 ID 和 4 阶段工作流 |
| **阶段/门禁** | PRD / 技术方案 / 实施 / 代码评审 4 个线性阶段，前置审批才能推进 |
| **Agent** | AI 执行代理（Codex / CodeBuddy / Qoder / Qwen） |
| **动作** | Agent 可执行的 15 种操作（如 PRD 分析、代码评审等） |
| **产物/Artifact** | 每个 AI 动作的输出文档（Markdown / HTML / 图片等） |
| **OpenSpec** | 结构化变更管理框架，包含提案、设计、任务三件套 |
| **变更** | OpenSpec 中的变更容器，一个需求对应一个变更 |
| **审批** | 人工对 AI 产出的审核决策（通过 / 驳回 / 风险接受） |
| **并发锁** | 同一需求同时只允许一个用户编辑 |
| **产物同步** | 将本地 AI 产物通过 Git 推送到团队共享仓库 |
