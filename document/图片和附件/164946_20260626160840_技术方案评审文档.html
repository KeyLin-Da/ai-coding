0. 设计边界与结论

本次技术设计只覆盖后端，不包含前端页面、海报绘制、交互动画和前端埋点实现。埋点由前端按数据侧 SDK 或神策规范直接上报，后端不新增 /events、埋点透传或服务端采集接口；后端只返回页面展示所需的业务上下文字段，前端可据此组装埋点属性。

采纳本轮评审意见，在线后端接口收敛为两类职责，并统一使用 member-points 语义路径：

  • 榜单主页数据接口：GET /api/v2/rank/member-points/list，只返回当前筛选条件下的 TOP50/TOP3、空态、本人成长值/排名和页面上下文；不返回悬浮入口配置，不做人群包入口计算，且不接收 source 入参。用户点击分享榜单时，不再新增或调用独立海报排行数据接口；前端必须使用当前筛选条件下的 list 响应数据绘制个人上榜海报和当前维度 TOP10 海报，必要时先用当前筛选条件重新请求一次 list 保证与首页展示一致。
  • 悬浮入口配置接口：GET /api/v2/rank/member-points/floating-config，读取 common.common-data-map 中的排行榜入口数组，按 visible、URL 和人群包规则过滤后直接返回入口数组；接口响应不返回 visible、crowdNos、enabled 等配置态字段，且不接收 source 入参。

地区筛选列表不再设计在 opp-learn 内聚合。按本轮批注，前端入口由 opp-learn-bff 提供 GET /api/v2/sale/branch、GET /api/v2/sale/region，BFF 再消费 opp-basic 对应销售组织主数据接口。销售组织数据来源已明确为 opp-basic 侧 cbs_sale_branch_info 和 cbs_sale_region_info；选中地区在某周期没有排行时，由榜单主页接口返回空榜单和空态。

主页榜单数据必须由服务端基于当前登录态判断用户身份，不能信任前端传入的 userNo、userType 或“是否业务人员”标记。按本轮确认口径：所有用户均允许查看排行榜；“业务人员”建议按 userType=DEALER 且 dealerType not in (11) 判断，即排除优惠消费者身份；员工、注册会员、dealerType=11 优惠消费者等非业务用户不展示本人上榜信息，也不生成个人上榜海报。海报分享权限由当前 list 响应判断：业务人员点击分享时，仅根据当前页面所选时间周期和地区维度下的 self.inTop50 判断本人是否在该维度进入 TOP50；命中则前端可用 self 和当前筛选上下文绘制个人上榜海报。所有可访问用户均可按当前 rankList 前 10 名绘制当前维度 TOP10 海报，不再自动补查分公司、区域、全国三个默认维度。若当前维度本人无个人海报且 rankList 为空，前端直接 toast：你当前选择的时间和地区暂无人上榜～。

分享海报二维码由前端处理。后端不返回 qrCode、二维码图片、短链、二维码有效期等字段；后端仅返回海报绘制所需榜单数据、配置和回流上下文。二维码内容由前端按页面路径和筛选上下文生成。

配置不新增独立 Nacos dataId，复用现有 common.common-data-map。排行榜规则说明、成长值说明、上榜有礼、推荐学习装修页地址，上榜有礼/推荐学习人群包 ID，悬浮入口配置和海报配置均放入该公共配置。

排行榜统计不在在线接口内实时聚合。数据处理小组负责按本文 SQL 口径产出榜单统计结果和组织归属快照；后端在线服务只读取已发布的统计结果表或视图，不再以 base_member 作为本需求当前季度实时组织关系的权威数据源。统计结果表命名调整为 edu_member_points_rank_snapshot；发布控制表优化为通用快照发布表 edu_snapshot_publish，只保存 snapshot_no、snapshot_type、发布状态、发布时间、数据截至时间等通用字段，不保存周期、维度、地区、用户、排名等排行榜业务字段，业务结果表通过 snapshot_no 关联发布记录。

补充本轮批注后，在线服务对“本人固定栏”采用双来源：排行榜排名和 TOP50/TOP10 列表只读数据处理产出的快照表；当 ETL 为控制数据量只产出 TOPN 或部分排名、导致当前业务人员本人 rankNo 查不到时，接口返回 rankNo=-1，前端按 99+ 兼容展示，同时后端按相同周期从 edu_member_points_detail 补算本人成长值。该补算只用于本人固定栏和冲榜差值，不参与榜单排序和排名计算。

榜单数据时效按 h+1 处理，每小时刷新一次。例如 12 点发布截至当天 11 点整的数据，接口 updateTime 返回当天 11 点整；0 点发布截至昨日 23 点的数据，接口 updateTime 返回昨日 23 点整。后端不再返回 updateTimeText，页面展示文案由前端基于 updateTime 统一处理。海报不再有独立后端数据版本，前端按当前 list 响应的 updateTime 绘制。

3.3 成长值统计 SQL 口径

变量说明：

  • :period_start：周期开始时间，闭区间。
  • :period_end：周期结束时间，开区间。
  • 组织归属：由数据处理小组 ETL 同步后的组织宽表/视图或统计快照提供，不以 base_member 作为本需求权威组织源。
  • detail_status=1：只统计获取积分。
  • points > 0：本期成长值只统计正向获得积分；兑换/消耗类 detail_status=0 不计入。
  • is_deleted=0 and status=1：只统计有效记录。

基础用户成长值聚合示例。下方 member_org 代表数据处理小组 ETL 同步后的会员组织宽表/视图，字段名仅用于说明口径，最终表或视图由数据处理小组确认：

SELECT
    m.id_card AS user_no,
    m.user_name AS user_name,
    m.portrait AS avatar,
    m.sale_region_no,
    m.sale_region_desc,
    m.sale_branch_no,
    m.sale_branch_desc,
    SUM(d.points) AS growth_value,
    MAX(d.create_time) AS reach_time
FROM edu_member_points_detail d
JOIN member_org m ON m.member_id = d.create_user
WHERE d.is_deleted = 0
  AND d.status = 1
  AND d.detail_status = 1
  AND d.points > 0
  AND d.create_time >= :period_start
  AND d.create_time < :period_end
  AND m.is_deleted = 0
GROUP BY
    d.create_user,
    m.id_card,
    m.user_name,
    m.portrait,
    m.sale_region_no,
    m.sale_region_desc,
    m.sale_branch_no,
    m.sale_branch_desc;

同成长值排序口径：

  • 主排序：growth_value DESC
  • 同成长值：reach_time ASC
  • 兜底稳定排序：user_no ASC

MySQL 8 窗口函数版本：

WITH user_growth AS (
    SELECT
        m.id_card AS user_no,
        m.user_name,
        m.portrait AS avatar,
        m.sale_region_no,
        m.sale_region_desc,
        m.sale_branch_no,
        m.sale_branch_desc,
        SUM(d.points) AS growth_value,
        MAX(d.create_time) AS reach_time
    FROM edu_member_points_detail d
    JOIN member_org m ON m.member_id = d.create_user
    WHERE d.is_deleted = 0
      AND d.status = 1
      AND d.detail_status = 1
      AND d.points > 0
      AND d.create_time >= :period_start
      AND d.create_time < :period_end
      AND m.is_deleted = 0
    GROUP BY d.create_user, m.id_card, m.user_name, m.portrait,
             m.sale_region_no, m.sale_region_desc, m.sale_branch_no, m.sale_branch_desc
)
SELECT
    *,
    ROW_NUMBER() OVER (
        ORDER BY growth_value DESC, reach_time ASC, user_no ASC
    ) AS country_rank_no
FROM user_growth;

区域榜：

SELECT
    *,
    ROW_NUMBER() OVER (
        PARTITION BY sale_region_no
        ORDER BY growth_value DESC, reach_time ASC, user_no ASC
    ) AS region_rank_no
FROM user_growth
WHERE sale_region_no IS NOT NULL
  AND sale_region_no <> '';

分公司榜：

SELECT
    *,
    ROW_NUMBER() OVER (
        PARTITION BY sale_branch_no
        ORDER BY growth_value DESC, reach_time ASC, user_no ASC
    ) AS branch_rank_no
FROM user_growth
WHERE sale_branch_no IS NOT NULL
  AND sale_branch_no <> '';

达成时间说明：

  • 在本期所有统计记录均为正积分时，用户达到最终 growth_value 的时间等价于本周期最后一笔正向积分 MAX(d.create_time)。
  • 如果未来成长值口径允许扣减、撤销或负数，需要改用累计流水窗口函数计算“第一次累计值达到最终值”的时间，不能继续用 MAX(create_time)。

4. performance（性能考量）

4.1 性能目标

场景 目标
榜单主页数据接口 P95 < 250ms，不含网关和客户端网络
地区列表接口 P95 < 200ms

4.2 核心策略

  1. 在线接口不做全量实时排名，不在请求内扫描 edu_member_points_detail 生成排行榜。
  2. 数据处理任务预先生成全国、区域、分公司三个维度排名，在线只读结果；仅当当前业务人员本人快照排名缺失时，允许按当前登录用户映射 ID、周期和 data_end_time 单用户补算 self.growthValue。
  3. 主页接口不读取 Nacos 和人群包，不返回海报专用结构，首屏只承担榜单渲染所需数据；分享海报复用该响应。
  4. 悬浮入口配置独立查询，直接读取并解析 Nacos 当前配置，不新增 Redis 配置缓存；人群包复用已有 10 分钟缓存；接口失败不影响主页榜单展示。
  5. 海报数据不新增后端查询；前端复用当前 list 响应的 rankList/self/updateTime，避免每次点击分享时拉取无关维度 TOP10 和无关维度个人排名。
  6. TOP50、本人快照排名、第50名成长值在服务端内部使用同一 snapshotNo，可在服务层并行查询后组合；本人快照缺失时的 self.growthValue 补算必须使用同一发布快照的 data_end_time 作为时间边界；self.quarterTop50 使用当前自然季度本人所属分公司对应发布快照查询，和当前筛选维度解耦。
  7. Nacos URL 配置为空时不调用外部内容渠道服务，直接隐藏入口。

4.3 大数据量风险

edu_member_points_detail 是流水明细表，按季度/年度全表聚合会随历史增长明显变慢。统计侧应至少保证：

  • edu_member_points_detail(create_time, detail_status, status, is_deleted) 有可用索引或分区。
  • 聚合过程按周期增量或分批处理，避免高峰期大事务。
  • 发布结果表与在线服务库之间存在明确的数据同步和回滚机制。
  • edu_member_points_rank_snapshot 按周期、维度和版本具备清理策略，避免历史版本无限增长导致索引膨胀。

5. concurrency（并发问题处理）

5.1 统计发布并发

数据处理发布统计结果时不能让在线接口读到半成品。统计刷新频率按 h+1，每小时发布一次，例如 12 点发布截至当天 11 点整的数据。建议：

  1. 新批次生成全局唯一 snapshot_no，先写入 edu_member_points_rank_snapshot 等业务结果表；写入期间不在 edu_snapshot_publish 中发布为 PUBLISHED。
  2. 数据处理完成行数、重复排名、TOP50 连续性、data_end_time 等校验后，写入或更新 edu_snapshot_publish(snapshot_no, snapshot_type='MEMBER_POINTS_RANK', status='PUBLISHED')。
  3. 在线服务先查 edu_snapshot_publish 最新 PUBLISHED 快照号，再按 snapshot_no 读取排行榜结果表。
  4. 旧 snapshot_no 可保留至少 1-2 个周期用于回滚；回滚时只需将通用发布表指回旧快照，不需要修改排行榜结果数据。

5.2 在线接口并发

  • 筛选快速切换由前端只保留最后一次请求结果；后端接口幂等。
  • 主页、悬浮配置、海报数据拆分后允许前端并行或按需调用；主页失败不应被悬浮配置失败牵连，悬浮配置失败也不应阻断榜单。
  • 排行榜主页和海报排行接口不使用 Redis 结果缓存；并发请求均读取当前已发布 snapshotNo，响应内必须返回 updateTime，服务端日志和内部上下文保留 snapshotNo，避免用户误解。
  • 人群包缓存为空集合也缓存 10 分钟，避免未命中用户反复调用会员中心。
  • Nacos common.common-data-map 配置更新与接口读取可能短暂不一致，依赖 Nacos 客户端本地缓存和刷新机制；解析失败时隐藏入口并报警，可在进程内使用最近一次有效配置兜底，但不写 Redis。
  • 海报不新增后端结果缓存；个人海报只由当前 list.self 派生，TOP10 海报只由当前 list.rankList 前 10 名派生，避免个人上榜信息泄露给非业务用户。

5.3 排名一致性

  • 主页 TOP50、本人快照排名、第50名成长值必须使用同一个 snapshotNo；本人快照缺失时补算 self.growthValue 必须使用该版本 data_end_time 对齐。
  • 海报 TOP10、个人上榜海报与页面 TOP50 使用同一个 list 响应、同一当前筛选维度和排序字段。
  • 如果前端先打开页面、后点击分享，默认按当前页面持有的 list.updateTime 绘制；如前端策略要求刷新，则只需按当前筛选条件重新请求 list，不调用独立海报接口。
  • 若本人已在 TOP50，底部本人固定栏是否展示取决于 selfVisible=true；非业务用户即使命中统计结果，也不返回本人上榜信息。
