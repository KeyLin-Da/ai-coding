从多种来源读取产品需求文档（PRD），并生成结构化的功能点清单。

---

## 输入格式

`/coding-prd-analyzer id=<requirement-id> [c=<clarification-desc>] [<source1>,<source2>,...]`

参数说明：
- `id=<requirement-id>`: （必填）需求ID，用于组织需求文档和输出目录。支持数字、字母、连字符、下划线，特殊字符将自动过滤
- `c=<clarification-desc>`: （可选）需求澄清描述，用于补充分析时的业务前提、范围边界和已确认约束
- `<source1>,<source2>,...`: （可选）逗号分隔的 PRD 来源列表

每个 source 可以是：
- **飞书文档**: `https://*.feishu.cn/docx/*` 或 `https://*.larksuite.com/docx/*`
- **蓝湖公开页面**: `https://*.lanhu.app/*`
- **墨刀公开页面**: `https://*.modao.cc/*`
- **Axure公开页面**: `http://axure*/*`
- **本地图片**: `/path/to/mockup.png`, `.jpg`, `.jpeg`
- **本地 PDF**: `/path/to/prd.pdf`

参数位置灵活：`id=` 和 `c=` 参数可以在源列表之前或之后。例如：
- `/coding-prd-analyzer id=167023 c=本期只覆盖B端管理端 飞书链接,蓝湖链接`
- `/coding-prd-analyzer 飞书链接,蓝湖链接 id=167023 c=暂不包含移动端`
- `/coding-prd-analyzer id=167023 飞书链接,蓝湖链接 c=仅保留MVP核心流程`
- `/coding-prd-analyzer c=短信验证码登录不支持国际区号 飞书链接,蓝湖链接 id=167023`

多个来源用逗号（`,`）分隔。skill 会处理所有来源并将结果合并为一份功能点清单。

当未提供 `source` 时：
- 若提供 `id=`，优先定位 `docs/{需求编号}/prd/analysis.md`，基于现有需求文档执行需求澄清
- 若未提供 `id=`，提示用户必须提供需求编号
- 若目标 `analysis.md` 不存在，提示用户补充 `source` 或指定正确的 `id=`

## 需求澄清描述参数规则

当提供 `c=<clarification-desc>` 参数时，系统将其作为分析上下文进行处理，并写入输出文件元数据与“澄清历史”章节：

### 验证规则
- **空值处理**: `c=` 后无内容将被忽略，视为未提供澄清描述
- **长度限制**: 建议不超过 500 字符，超长内容可截断后写入
- **安全处理**: 移除文件系统危险字符和无效控制字符

### 使用规则
- 仅用于补充分析语义，不参与目录命名
- 可描述范围边界、排除项、业务前提、术语定义
- 会在功能点分析中优先用于约束功能范围判断
- 在无 source 澄清模式下，必须作为本次澄清记录追加到 `analysis.md` 的“澄清历史”章节

---

## 参数优先级

当同时提供 `id=` 和 `c=` 参数时，目录命名使用需求ID，其中 `c=` 不参与目录命名，但会记录到输出文件元数据中。

- **提供 `id=`**: 使用需求ID作为目录名
- **提供 `c=`**: 不改变目录名，仅补充分析上下文
- **未提供 `id=`**: 拒绝执行，提示用户必须提供需求编号

## 需求ID规范化与验证

当提供 `id=<requirement-id>` 参数时，需求ID将经过验证和规范化处理：

### 验证规则
- **空值处理**: `id=` 后无内容将被忽略，视为未提供需求ID
- **长度限制**: 需求ID超过 50 字符将被截断，保留有意义部分
- **危险字符过滤**: 文件系统危险字符（`../`, `*`, `?` 等）将被移除或替换
- **字符集限制**: 仅允许数字、字母、连字符、下划线、点号

### 规范化规则
- 移除或替换危险字符为下划线
- 保留数字、字母、连字符、下划线、点号
- 示例转换：
  - `167023` → `167023`
  - `feature/login-v2` → `feature_login-v2`
  - `bug#123` → `bug_123`

规范化后的需求ID将用于创建输出目录。

### Step 0：参数校验

**必须首先校验参数完整性：**
- 检查是否提供了需求编号 `id`
- **如果未提供需求编号，立即停止执行，并提示用户：**
  ```
  ❌ 错误：缺少必填参数「需求编号」
  
  请提供需求编号，例如：
  /coding-prd-analyzer id=167023 飞书链接,蓝湖链接
  ```
- 只有在校验通过后，才继续执行后续步骤

## 内容提取策略

### 无 source 的澄清模式

1. 按参数优先级定位既有需求文档：`id > n > default`。
2. 读取目标 `analysis.md` 与同目录 `files/` 中的缓存资料（截图、HTML、副本文件等），将 `files/` 资料作为澄清证明依据。
3. 若 `analysis.md` 中存在需求来源链接（如 frontmatter 的 `prd_sources` 或正文中的可识别 URL），尝试重新获取最新资料并写入 `files/`，用于与历史资料交叉验证。
4. 若重新获取失败，则回退使用本地 `files/` 缓存继续澄清，并在结果中标注“已尝试刷新来源但失败”。
5. 结合 `c=<clarification-desc>`、`analysis.md`、`files/` 缓存和可用的最新资料执行需求澄清分析。
6. 将澄清结果写回同一需求目录的 `analysis.md`（单需求单文档维护），并在澄清结论中引用证据来源（`files` 文件名/来源链接）。
7. 保留既有“澄清历史”记录并追加下一版本；若旧文档没有该章节，必须补建章节后记录本次澄清。
8. 澄清历史只保存摘要、影响范围和处理结果，不嵌入完整旧版 PRD 正文；完整差异依赖 Git/产物版本追溯。

### 飞书文档

1. 使用 `lark-doc` skill 读取文档内容。
2. 如果访问被拒绝，报告错误并提示检查文档分享权限。
3. 提取所有文本内容用于功能点分析。

### 蓝湖 / 墨刀公开页面

1. 使用 `Browser Automation` 或 `playwright-cli` 或者 `curl` 打开公开链接。
2. 等待页面完全加载。
3. 截取页面截图。
4. 使用视觉理解能力分析截图，识别 UI 元素、表单、按钮、表格、卡片和功能描述。
5. 如果页面加载失败，报告错误并提示检查链接或保存为本地图片后重试。

### Axure公开页面

1. 使用 `curl` 获取公开链接。
2. 等待页面完全加载。
3. 截取页面截图。
4. 使用视觉理解能力分析截图，识别 UI 元素、表单、按钮、表格、卡片和功能描述。
5. 如果页面加载失败，报告错误并提示检查链接或保存为本地图片后重试。

### 本地图片

1. 使用 `Read` 工具读取图片文件。
2. 使用视觉理解能力分析图片，识别 UI 元素和功能描述。
3. 如果文件不存在，报告错误。

### 本地 PDF

1. 使用 `pdf` skill 提取文本和/或截取页面截图。
2. 使用视觉理解能力（针对截图）或文本分析（针对提取的文本）分析内容。
3. 如果文件不存在或无法读取，报告错误。

## 错误处理

对每个来源，处理以下错误场景：

- **权限不足（飞书）**: "无法读取飞书文档，请检查文档分享权限。"
- **页面加载失败（蓝湖/墨刀）**: "无法加载设计稿页面，请检查链接是否有效，或保存为本地图片后重试。"
- **文件不存在（本地）**: "文件不存在: `<path>`"
- **无法识别的来源类型**: "无法识别的 PRD 来源: `<source>`。支持的格式: 飞书文档链接、蓝湖/墨刀公开链接、本地图片(.png/.jpg/.jpeg)、本地PDF(.pdf)"
- **未提供 source 且未找到需求文档**: "未提供 PRD 来源，且未找到可用于澄清的需求文档（analysis.md）。请提供 source，或指定正确的 id=/n=。"
- **来源链接刷新失败（澄清模式）**: "已定位到需求文档，但从历史需求链接刷新最新资料失败，将基于本地 files 缓存继续澄清。"

## 功能点结构化

### 提取维度

对每个识别出的功能点，提取以下维度：

- **类型**: `页面` | `弹窗` | `组件` | `流程`
- **角色**: 使用此功能的用户角色（如运营人员、C端用户、系统管理员）
- **用户故事**: 作为[角色]，我想要[能力]，以便[达成什么业务目标]
- **优先级**: P0(必须) | P1(应该) | P2(可以) | P3(本期不做)
- **描述**: 该功能做什么（纯业务视角，不涉及技术实现）
- **交互步骤**: 用户操作的有序列表
- **输入数据**: 业务层面的字段及含义（必填/选填、格式限制、取值范围）
- **状态变化**: 数据或状态的业务流转
- **异常场景**: 业务边界情况和处理方式（含提示文案）
- **验收条件**: Given-When-Then 格式的可测试验收条件（P0 功能点必填）
- **关联功能**: 与其他功能点的交叉引用
- **参考截图**: （可选）UI 设计稿或原型截图路径

### 功能点识别规则

- 以**页面**为首要组织维度，所有功能点归属于其所在的页面
- 每个**独立可操作的页面**作为一个页面章节
- 页面内的每个**可独立描述的业务操作或交互**作为一个功能点
- **列表页**和**详情页**分属不同页面章节
- 跨页面的业务流程归入「跨页面流程」独立章节
- 不单独提取后端接口功能点——后端服务能力由页面功能点的输入数据/状态变化/异常场景隐含推导，属于技术方案设计范畴

### 页面维度组织

按页面组织功能点。一个页面章节对应 PRD 中一个完整的用户界面（后台页面、C端页面等）。页面是需求分析最自然的组织单元——PRD 来源（蓝湖/墨刀/Axure）本身就是按页面呈现的，用户也是在页面上完成操作。

### 参考截图管理

#### 截图保存策略

对于涉及 UI 样式的关键功能点（页面、弹窗、组件），必须保存参考截图：

1. **来源为设计稿链接（蓝湖/墨刀/Axure）**：
   - 使用 Browser Automation 截取完整页面或关键区域
   - 保存到 `docs/{需求编号}/prd/files/screenshots/` 目录
   - 文件命名规则：`{页面名}_{功能点名称}_{时间戳}.png`
   - 示例：`user-management_login-page_20260521.png`

2. **来源为本地图片**：
   - 复制原始图片到 `docs/{需求编号}/prd/files/screenshots/` 目录
   - 保持原始文件名或按上述规则重命名

3. **来源为飞书文档/PDF**：
   - 如文档中包含 UI 截图，提取并保存到 `screenshots/` 目录
   - 如无可提取的截图，标记为"无参考截图"

#### 截图引用规范

在功能点描述中引用截图时使用 Markdown 图片语法：

```markdown
![功能点名称](files/screenshots/{截图文件名})
```

示例：
```markdown
### 登录页面

**参考截图**：
![登录页面](files/screenshots/user-management_login-page_20260521.png)

**描述**：用户输入账号密码进行身份验证

**交互步骤**：
1. 输入手机号/邮箱
2. 输入密码
3. 点击"登录"按钮
```

#### 关键功能点判定标准

以下类型的功能点**必须**附带参考截图：
- ✅ 所有**页面**类型功能点（列表页、详情页、表单页等）
- ✅ 所有**弹窗**类型功能点（确认对话框、信息弹窗等）
- ✅ 复杂的**组件**（含多个交互元素的复合组件）
- ❌ 抽象的**流程**描述（除非包含具体 UI 步骤）

### 结构设计说明

- **页面先行**：页面是需求分析最自然的组织单元，PRD 来源本身就是按页面呈现的
- **跨页面流程独立**：不属于任何单一页面的流程单独成章，不打断页面阅读连贯性
- **不包含技术内容**：只描述"做什么"和"为什么做"，不描述"怎么做"——后端接口、数据结构、实现策略属于技术方案设计范畴
- **业务规则集中索引**：便于评审和下游技术方案逐条对照覆盖
- **验收条件 GWT 格式**：确保每个 P0 功能点可测试可验证，为 OpenSpec specs 提供直接支撑
- **澄清历史追加**：初始生成写入 `v1`；每次无 source 澄清按 `v2、v3...` 追加记录，记录本次澄清描述、影响范围、处理结果和运行记录（如可获取）

### 文件位置

根据需求ID，输出目录结构如下（单需求单文档，不再创建时间戳目录）：

#### 标准输出路径
`docs/{需求编号}/prd/`
├── analysis.md
└── files/
    └── (中间文件缓存)

其中：
- `{需求编号}` 是规范化后的需求ID

示例：

## 实现说明

- 尽可能并行处理多个来源
- 输出文件设计为可人工编辑 — 使用列表格式而非表格
- 视觉理解准确率取决于 PRD 清晰度；始终将输出标记为"需审查"

## 向后兼容性

### 参数支持
- 新增 `id=` 参数（需求ID），必填
- 新增 `c=` 参数（需求澄清描述），用于补充分析上下文
- 移除 `n=` 参数（需求名）

### 兼容性保证
1. **新分析任务**：所有新分析任务统一写入 `docs/{需求编号}/prd/analysis.md`
2. **历史文件访问**：历史目录文件仍可访问，不会被自动移动或删除
3. **历史章节补建**：历史 `analysis.md` 缺少“澄清历史”章节时，下一次澄清应自动补建该章节并追加当前记录
